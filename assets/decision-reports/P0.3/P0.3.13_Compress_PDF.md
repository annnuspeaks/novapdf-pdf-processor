# P0.3.13 — Compress PDF Decision Report

**Project:** Nexora PDF Tools  
**Status:** Proposed; validate dependencies and test before marking Approved  
**Priority:** Conditional MVP

## 1. Purpose
Attempt to reduce PDF file size without promising a fixed compression ratio.

## 2. User Workflow
1. Open the dedicated tool page.
2. Upload/select input and configure the minimum required options.
3. Validate the input and show actionable errors.
4. Process the file and show a loading state.
5. Show a result/preview or output details on the same page.
6. Download the output directly.

## 3. Input and Output
- **Input:** One PDF
- **Output:** One optimized PDF
- **Result page:** Not required; the workflow remains on the tool page.

## 4. Free Implementation
- **Preferred approach/dependencies:** pypdf for basic optimization; optional Ghostscript requires separate license/deployment review.
- **Paid API:** None permitted.
- **Important licensing note:** Verify the exact dependency version, license obligations, and deployment compatibility before release. “Free to download” does not automatically mean suitable for every hosted/commercial use.

## 5. Implementation Approach
First test pypdf optimization for stream/object compression. If stronger image recompression is required, assess an optional system tool separately; do not silently rasterize pages.

- **Frontend:** React + Vite dedicated route.
- **Backend:** FastAPI where server-side processing is required; use a consistent `/api/tools/...` route naming convention.
- **Future Android:** Keep processing in a documented, UI-independent service/endpoint where practical.

## 6. Validation and Error Handling
- Validate extension, actual file content, file count, and size.
- Reject unsupported, corrupt, or unreadable input with a clear message.
- Show loading, success, and error states.
- Do not expose internal paths, stack traces, or file contents in logs.
- Use temporary per-job files and clean them up after completion.

## 7. Security and Limits
- **Initial limits:** Set practical upload, file-count, page-count, and processing-time limits before deployment.
- **Privacy:** Process only the uploaded files needed for the request; avoid retaining them after processing.
- **Resource protection:** Add timeouts and safe failure handling. Do not run uploaded macros or arbitrary embedded code.

## 8. MVP Scope
MVP: safe basic optimization and before/after size. Defer aggressive lossy image recompression until separately tested.

## 9. Acceptance Criteria
- [ ] A dedicated page supports the documented input and output.
- [ ] Invalid input produces a clear, actionable error.
- [ ] Valid input produces a file that opens and matches the requested operation.
- [ ] The output downloads directly from the same page.
- [ ] Temporary files are cleaned up.
- [ ] Desktop and mobile layouts remain usable.
- [ ] No paid API/service is required.
- [ ] Dependency license and deployment requirements are checked.

## 10. Risks and Open Decisions
- **Risks / constraints:** Compression gains vary by document. Preserve legibility and explain when output is not smaller; never promise lossless or guaranteed size reduction without testing.
- **Open decision:** Confirm dependency/license and test representative valid, invalid, and edge-case files.
- **Decision:** Proposed, pending implementation test.
